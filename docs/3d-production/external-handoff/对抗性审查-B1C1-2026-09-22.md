## 一、审查方式（刻意不读自己的结论）

对抗性审查的关键是**独立重推导**。本轮的做法是：

1. 写一个只读脚本 `output/external-handoff/adversarial/adversarial_audit.py`，**直接从源取证**——
   Godot 源码行、`.glb` 二进制（自己解析 glTF 的 JSON chunk 与 BIN chunk，对 POSITION / JOINTS_0 / WEIGHTS_0 取 sha256）、
   `content.json`、`transitions.json`、`collect_coverage.py`、`props-export.json`、CSV——
   **而不是回头读交付文档里写的数**。
2. 每条主张给 3 态：`CONFIRM`（独立复现一致）/ `REFUTE`（被反例推翻）/ `WEAK`（证据不足或表述过强），并**打印实际观测值**。
3. 脚本自身出过错（见 §四），修好后**重跑到 0 个 REFUTE / 0 个 WEAK** 才算通过。
4. 脚本无法覆盖的部分（如"是否真的能打开游戏"）单独列出边界，不冒充已验。

**结果**：该轮独立检查 **全部 CONFIRM**（0 REFUTE / 0 WEAK），另 1 项为口径统计（INFO）。过程中发现 **3 处交付物缺陷**（全部已修）+ **4 处值得报给主 Agent 的脆弱点**。

> **⚠️ 关于"多少项"这个数字（2026-09-22 晚补注）**：本报告成稿时该轮为 **45 项**。此后脚本为 C2 返修陆续新增检查，**重跑实测：45 → 49 → 51**（每加一项就变一次）。**条数会随脚本增删漂移，不是验收指标**——判定只认 `REFUTE = 0` / `WEAK = 0`。主 Agent 文件里写的"45 项通过"指的是**成稿那一轮**，与本报告口径一致；**引用时请用"该轮 N 项、全部 CONFIRM"的写法，不要锚定某个数字。**

> **⚠️ 这个"全部通过"能证明什么、不能证明什么（2026-09-22 晚按主 Agent 限定补注）**
> - **能证明的**：**我自己的静态检查**——被审文档里那些**可从源码/资产/机器可读目录复核**的事实性断言，经独立重推导后一致。
> - **不能证明的**：**整个交付通过**。它**不是** Phase 1 的门槛验收，**不含**任何运行时验证（没跑测试、没开游戏、没真人试玩、没性能数据），也**不能**替代 `production-gates.md` 的五条门槛。
> - 换言之：全部 CONFIRM 只说明"**没有发现与前一轮同等量级的事实错误**"，**不等于**"交付已验收"。引用本报告时**不得**省略这一限定。

```
$ python3 output/external-handoff/adversarial/adversarial_audit.py
汇总： {'CONFIRM': 45, 'INFO': 1}   # 成稿那一轮
汇总： {'CONFIRM': 49, 'INFO': 1}   # C2-a…C2-d 加入后
汇总： {'CONFIRM': 51, 'INFO': 1}   # C2-e / C2-f 加入后
# ↑ 三行是三次真实运行输出，用来展示"条数在涨"。**不要再把这个数字当复现目标**：
#   以后每加一条检查它就会变。判定口径只有一条：REFUTE = 0 且 WEAK = 0。
$ python3 output/external-handoff/C1/verify_links.py   # 链接自检，EXIT=0
✅ 无两级解析都失败的引用
```

> **三次都是 `REFUTE 0` / `WEAK 0`**——条数从 45 涨到 51 是脚本变多，不是结论变化。

## 二、发现的 3 处缺陷（全部已修）

### 缺陷 1（较重）`firstAggressionDiscount` 一行的"0 命中"与**自己给的复现命令**互相打架

- **修订前**：`B-content-assets/README.md` §2.5 与 `corrections.md` B1-7 都写该字段"**0 处命中**／**4 处硬编码 10**"，并给出一条复现命令：
  ```sh
  grep -rn --include='*.gd' -e firstAggressionDiscount -e signatureReward -e publicInfo … Godot/three_d
  ```
- **反例（独立复核）**：这条命令实际返回 **12 行**。原因是 `Table` 有一个**同义的运行时状态键** `firstAggressionDiscountAvailable`（`table.gd:26/67/94/96`、`table_hud.gd:201`，以及 6 个测试行）。主 Agent 只要复制粘贴这条命令，就会看到 12 与表里的 0 直接冲突。
- **附带错误**："4 处硬编码 `10`"也**漏计**：实际**字面量 `10` 共 7 处**——生产 2（`rules/table.gd:67`、`scripts/table_hud.gd:201`）+ 测试 5（`tests/raise_preview_test.gd:19`、`tests/poker_action_coverage_test.gd:32`、`tests/poker_guard_coverage_test.gd:29/30/31`）；另 2 处断言把折扣写进期望值（`tests/table_test.gd:67`、`tests/two_tables.gd:26`）。原写法还把 `table.gd:26`（**桌名门**，里面没有字面量 `10`）算进了"硬编码 10"，属口径混杂。
- **结论**：字段名 0 命中**是真的**，折扣功能在跑**也是真的**——**两者必须分开写**。
- **已修**：
  - `README.md` §2.5 该行改为三口径并列（内容字段名 0 / 同义状态字段 12 行 / 字面量 `10` 7 处 + 桌名门 1 + 断言 2），并加"**不要把两者混成一次 grep**"的口径警告。
  - 复现命令**拆成三条**（6 个真零读字段 / 字段名 / 字面量），逐条与表格对齐。
  - `corrections.md` B1-7 拆成三行，并加显式的「⚠️ 审查后订正」说明原"4 处"错在哪。

### 缺陷 2（轻）`doc-corrections.md` 两处行号不精确

## 三、不是缺陷、但值得报给主 Agent 的 4 处脆弱点／边界

1. **酒保占位件的隐藏是"元数据驱动"的，缺元数据会静默失效。**
   `characters.gd:28-30` 靠 `node.get_meta("visual_role", "").begins_with("Bartender")` 决定隐藏；该元数据由 `world.gd:130-133 box()` 的 `set_meta("visual_role", node_name)` 写入，恰好因为 `bar_display.gd:13-15` 把盒体命名为 `BartenderTorso / BartenderHead / BartenderHand` 才匹配上。
   **风险**：将来若新增不带该元数据、或以别的前缀命名的酒保占位件，`hide()` 会**静默失效**（占位盒与 GLB 同时可见，且没有测试报错）——`art_integration_test.gd:20-22` 覆盖的是 `Floor/PokerTable/…/Bottle` 那批前缀，**不含 `Bartender*`**。（`characters_test.gd:32` 有断言，但它同样依赖同一个前缀判据。）
   反过来，这一点也让 B1-1 的结论**更硬**：实现与测试用**完全相同**的判据，属于可交叉验证的接线。

2. **`build_tavern()` 单一函数生成四间牌室 ⇒"4 套空间"的结论可复现，但"4 家酒馆"这个说法本身会误导。**
   实测：`world.gd:206` 只有 **1 个** `build_tavern()` 定义、`:79-82` **4 次**调用（offset 10/20/30/40）、`world.gd:51 ROOMS` **4 项**（`Tavern / LedgerCellar / MirrorHall / EmbersRoom`）。B 交付的表述（"同一建筑内的不同牌室，不是四/五套空间"）与此一致；但"酒馆"一词在内容层（`scenes`，4 家不同费率/货架的店）与空间层（同一外壳的 4 个房间实例）**指的不是同一个东西**，主 Agent 在跨文档引用时需注意。

3. **贵重物"0 独立模型"已有正面证据，但"未来是否需要"仍是产品决定。**
   正面证据：资产目录 25 个模型文件（13 `.glb` + 12 `.blend`）中，**没有任何一个**以 10 件贵重物的 id 命名；`stash.glb` 只有一个合并节点 `Valuables`。B 交付保留的三级写法（静态装饰 / 独立模型 / 背包奖励表现）与实测吻合。**但"Phase 3 要不要做体积差异"是产品判断，本审查不代答。**

4. **链接自检的"条数"不是稳定指标。**
   `verify_links.py` 报的反引号路径条数**每次编辑文档都会变**（本轮从 65 → 66 → 54 → 56 → 59 → 60）。把它当验收数字会被自己坑：**真正的判定标准是"0 条两级解析都失败"**（EXIT=0）。已把 `README.md` §六 的该行与 `corrections.md` 的输出块改为**只呈现判定行、刻意省略条数**。
   另：自检脚本会**刻意跳过**两类非引用文本（反引号里的"链接写法示例"、含空格的命令行）。因此**描述"错误写法"的反例不能再加反引号**——本轮就踩过这个坑（加了反引号 → 被计成 11 条假断链），已在两处文档写明这条写作约束。

## 四、审查工具自身的错误（已修，记录以示透明）

对抗性审查要求"**审查者也要被审**"。本轮脚本首跑给出了 **1 个 REFUTE + 4 个 WEAK**，逐个核查后**全部是脚本自身的误判**，遂修脚本后重跑：

| 脚本的误判 | 真实情况 | 修法 |
|---|---|---|
| `SUITES = 17` 判 REFUTE（正则只认双引号键，源文件用单引号） | 实为 **17** 键 ✅ | 正则改 `'([^']+)'\s*:` |
| `酒保已接线` 判 WEAK（想在单行里匹配 `bartender.*\.glb`，但 `actor()` 是**通用加载器** `load("…/" + id + ".glb")`，永远匹配不到） | 实为 **CONFIRM**（`characters.gd:27` 调 `actor("bartender", …)`，`:28-30` 隐藏占位） | 改判据为 `actor\(\s*"bartender"` + 元数据驱动检查 |
| `world.gd:94-99` 判 WEAK（断言行号算错一位） | 实为 **CONFIRM** | 修正断言行 |
| `sale_value` / 奖励 `match` 判 WEAK（断言过松，不比对观测值） | 实为 **CONFIRM** | 断言改为基于实际取到的行内容 |
| `transitions` 条目数判 REFUTE（把 list 直接和 252 比） | 实为 **252** ✅ | 取 `len()` |
| `transitions.json` 一度**静默跳过**（路径按 `Godot/three_d` 下找，实际在 `docs/3d-production/phase-1/coverage/`） | 补上 `docs` 回退 + 找不到时报 `REFUTE` 而非静默 | 加回退与失败可见化 |

> **教训（已写进脚本注释）**：审查脚本**必须让"跳过"可见**。一个静默跳过的检查会让报告看起来通过，实际什么都没验——这比误报更危险。
