# 对抗性审查：A7 复核与 A8 审计（自审）

2026-09-25。审查对象是本人本轮产出的两份交付：

- A7：`docs/3d-production/external-handoff/A7-seat-variant-review/README.md`（复核，不新建测试）
- A8：`docs/3d-production/external-handoff/A8-global-catalog-audit/README.md` + 3 份 CSV

审查方式是**尽量站到对立面**去打这两份结论，而不是复述它们。

## A. 打 A7 的结论

### A1 「48 个座位样本」证不了它想证的东西

座位维度是真实的（seat 0/1/2 走的是三段不同的前置动作路径，不是同一个夹具换参数）。**但 48 个样本里的短筹码状态，全部由测试直接改写 `stack` 字段构造**（`donor.stack += ...; actor.stack = needed`）。

所以这 48 个样本证明的是「规则引擎在这些人工状态下按座位正确」，**不能推出**「真实牌局里会走到这些座位组合」。原任务书要求的就是断言后继状态，这一点它做到了；但如果有人拿「48 个座位样本通过」去支撑「座位变体在真实玩法中已验证」，那是超读。

### A2 「590 项检查」的可信度

套件跑完 590 项检查只用了 **0.3 秒**。这个数字快到应该起疑，我做了一次反向确认：日志零 ERROR、退出码 0、报告被重写、总结行只在所有循环结束后才打印、报告里 48 个格子的 `checks` 都在 6～17 之间且网格完整无重复。

**我仍然不能 100% 排除个别循环被静默跳过。** 缓解证据是网格完备性（4×3×4，去重后仍 48），但那只能证明「登记了 48 格」，不能证明「每格内部每一条断言都真的执行到了」。要彻底排除，得让套件对每个格子输出独立的检查数并断言其下界——当前没有。

### A3 「不虚增分母」≠「覆盖增强」

座位样本**不注册任何目录命中**（`record_seat_case` 只写遥测）。这意味着它对「目录覆盖率」的贡献是 **0**。

A7 文档的字面是对的，但读者很容易把「48 个样本」误读成「新增了 48 条覆盖」。**这份复核特意在 §3.1 把机制写清楚，就是为了堵这个误读。**

### A4 「全回归 59/59」字面为真、可复现性为假

我用脚本默认参数（每套件 90 秒）复现，得到 **58/59**；抬到 180 秒才是 59/59。仓库历史里已留下两份因此变红的报告（`20260925-100737`、`20260925-102421`）。

**所以主线的声明缺了一个必要限定：只有在显式抬高超时时成立。** 这是本轮最实的产出之一。

### A5 我的核验器自己出过两次错

- **S6 误报 REFUTE**：源码把两个族名写在同一行三元表达式中（`record_seat_case("exact_call_all_in" if exact else "short_all_in", ...)`），我用整串字面量匹配，匹配不上就报错。已改为从调用里抽字符串字面量。
- **D1 误报 REFUTE**：`run_godot.py` 把 Godot 输出写进日志文件、不在自己的 stdout 回显，我却去读 stdout。已改为读日志文件。

**教训（已写进 A7 README 的「已知坑」）**：核验器自身的假阴性必须与被核验对象的缺陷分开呈现，否则会把工具 bug 当成被测对象的缺陷去汇报。

## B. 打 A8 的结论

### B1 「382/382 全部有归因」有一半是我自己追出来的

第一版合并后，**24 个目录 ID 没有任何审计行归因**。我随后派了一个专门的闭环任务（G5）把这 24 条逐条查清，才得到 382/382。

**这 24 行是「追认式」归因**——先知道存在这个 ID，再回头去找它在源码里的位置。它证明了「这些 ID 在源码里有对应分支」，**但它不能证明「如果从源码出发自然枚举，不会漏掉别的」**。

这是本审计**最大的方法学弱点**，必须写在明处。一个真正干净的完备性论证应该是：从源码枚举出 N 条分支，再去目录里找对应；而不是从目录的 382 个 ID 出发去回填。

### B2 「40 条未登记可达」是下限，不是上限

四路审计都是「通读函数体 + 逐分支判断」，**没有穷举状态空间**。服务动作 × 道具 × 牌桌状态的组合路径明确是推理结论，不是实测穷举。

所以 **40 只是「被读出来」的数量，不是「缺口总数」**。任何把 40 当作分母去算「遗漏率」的做法都是错的。

### B3 我的合并器吃过行，而且吃掉的正是最关键的那批

第一版 `merge_duplicate_mappings` 对 `catalog_id == '-'` 的行返回空列表，**整行被丢掉**——`reachable_unmapped` 一度从 40 掉到 1。

这是我自己引入的、**方向最危险**的 bug：它恰好会抹掉本审计最核心的证据（未登记但可达的结果）。已修，并加了守卫「合并前后键集合必须完全相等」，以及「无目录 ID 的行键里必须带上 `branch_or_guard`，不许合并」。

**如果我没加那个守卫，这份交付会以一个"看起来很干净"的假象交出去。**

### B4 「无重复映射」只在窄键上成立

我只检 `(source_file, source_line, catalog_id)` 这个三元组。**同一语义若被两个审计员写成不同的 `source_line`，我检不出来。**

已知的相邻风险：`search.*` 的 20 个 ID 同时被 g1（分派入口口径）和 g3（内部 apply 口径）归因，我判为「同一次转移的两半」而放行。**这个判定没有独立证据**，只是两个审计员各自的说法。如果它们其实是重复计数，我的核验器不会报。

### B5 `evidence_strength` 是主观标注，核验器只能查格式

`strong / weak / none` 的判据写进了给审计员的提示词，但**没有任何机器校验**。核验器只能确认取值合法，**查不了这个判断对不对**。

更糟的是：G1 有 2 行写了枚举外的值（`-` 和 `unknown`），我把 `-` **归一化成了 `none`**。这是把一个「不确定」强行变成「确定」，方向上属于**替审计员做了他没做的判断**。这条已在 README 的 notes 里留痕，但它是真实的方法学污点。

### B6 「可达 / 不可达」的判定是推理，不是实测

G5 里 8 条 `player_reachable=no` 的依据是调用链推理（例如入口在选择面板之外根本不出现、输入无法构造）。**没有一条是穷举实测证否的。**

### B7 证据报告的新鲜度只保证「路径存在」

审计期间 HEAD 前移 7 次、`output/3d/*-coverage.json` 被并发的多份回归重写过至少 3 次。

我做了逐文件 `git diff --numstat` 核验，确认**15 个被审源文件全程字节未变**（所以行号锚点有效）。但**证据报告本身在审计期间被重写过**——「evidence_report 路径存在」只保证路径在，**不保证审计员读到的版本与我核验时读到的是同一份**。

### B8 与主 Agent 交付不兼容，我没有承担合并决策

主 Agent 在同一目录并发产出 3 份同表头 CSV，但 `disposition` 取值体系与本报告不同，无法直接合并。我**只报告、不合并**——这是任务书要求的边界（不替主 Agent 做判断），但也意味着**这份交付单独拿出去是不完整的**：主 Agent 那 49 行 World 内容不在我的表里。

## E. 交付后复核追加（同日晚，2026-09-25）

用户要求「做完之后进行对抗性审查」之后，又做了一轮**复核**（读回自己的产物、重跑核验器、比对机检数字）。**这一轮抓出的 4 个问题全部发生在我自己的交付物里**，所以按同样标准记下来。

### E1 我在 A8 README 里亲手复制了 3 条断链

`verify_links.py` 报本目录 6 条断链：主 Agent 底稿 3 条 + **本报告 3 条**。

- 起因：§9.1 的表格把主 Agent 那三个**已损坏**的引用写成了反引号路径。按本项目惯例，反引号 = 「可打开的引用」，于是我把别人的坏链接抄成了自己的。
- 更糟的是**同页下文第 138 行明写「此处故意不加反引号」**——文档在 3 行之内自相矛盾。
- 已改为「」引用并留下纠错记录；复验后反引号条数 234 → 231（正好减去 3），本报告贡献 0 条断链。
- **教训**：记录别人的坏引用时，**不能用引用语法**。这与「不把已删除文件写成反引号路径」是同一条规矩的另一面。

### E2 A8 README 的模块计数手写少 1，且自相矛盾

§4 写 `advanced_services 45`，机检是 **46**。把 README 那 15 个数字相加得 **666**，而同页白纸黑字写着 `branch-inventory.csv` 有 **667** 行——**文档自己就反驳了自己**。

- 已改为 46，并做了 README 全文 15 个模块数字与 `a8-verify.json` 的逐项比对：**0 处不符，合计 667**。
- **这就是「手写条数会漂移」的又一实例**。这类数字要么机器生成、要么每次交付前逐项比对；否则 667 与 666 会并排躺在同一页上，而且没人会去加。

### E3 交付 JSON 的锚点字段全是 `null`

我在 `check_catalog_ids()` 里加了 `anchor_head` / `drift_added` 等返回字段，**但主流程没接住返回值**（`check_catalog_ids(...)` 直接丢弃结果），于是 `a8-verify.json` 里这些键一律是 `null`。

- 已改为 `attribution = check_catalog_ids(...)` 并写进 `result['catalog_attribution']`，现已能读到 `anchor_head` / `anchor_ids_total: 382` / `drift_added: ['start.partial_bankroll']`。
- **教训**：字段"存在"不等于字段"被填充"。这和我之前那条——「断言 `<容器>.<子控件>.size` 前先追谁填充它」——是同一个错误的不同外衣。

### E4 目录在交付之后又漂移，而漂移的正是我标出的缺口

| 项 | 交付锚点 | 复核时工作区 |
|---|---|---|
| HEAD | `8d8464e1` | `8d8464e1`（未变） |
| `transitions.json` | `087971c9…` / 382 ID | `0a3d8fe3…` / **383 ID**（modified，未提交） |
| 新增 | — | `start.partial_bankroll` |

**关键互证**：本清单 `unmapped-reachable.csv` 里早有一行 `Godot/three_d/rules/run.gd:61-62 | catalog_id = - | reachable_unmapped`；`run.gd:61` 就是 `bankroll = mini(int(content.standardBankroll), vault)`，与主线新登记的 `start.partial_bankroll` 是同一条。

- 对我有利：说明那 40 条**不是凑数的噪声**，而是可被主线直接采纳的缺口。
- 对我不利：这说明我的清单**同样是快照**，锚点一动就不再自洽；`382/382` 若不带锚点引用就是一发即倒的数字。
- 已把「漂移」与「漏采」做成语义相反的两条输出，并用合成数据做了正反测试（无漂移不误报 / 漂移不误判为漏采 / 真漏采仍报漏采 / 锚点 ID 被删硬报错）。

### E5 一次未能归因的哈希读数（如实记录）

复核过程中有一次读到 `branch-inventory.csv` `4521cfec…`、`unmapped-reachable.csv` `6c4fd87f…`（同一时刻 `unverified-or-unreachable.csv` 与最终值一致）。随后**四种交叉实验**——同环境连跑、换 `PYTHONHASHSEED`、换锚点版目录、关闭本轮新增的锚点逻辑——**都只能复现最终值**，且与原始构建的 stdout 逐字一致。

- 排除项：分片未变（mtime 与哈希与会话开始一致）、目录版本无关、脚本改动无关、哈希随机化无关、未排序首版也不匹配。
- **没有归因成功。** 因此只能说：当前交付内容可复现且与原始构建一致，那次读数的成因不明。考虑到本仓库交付目录**存在并发写入**（主 Agent 同目录产出、并有散装进程），已把这一点记进 README §2.3 并固化了分片与产物的 sha256，供下一轮比对。
- **不夸大也不隐瞒**：这**不影响**本审计的任何结论，但它是一个我解释不了的现象，理应留痕。
